## The two bugs the closed-loop simulation caught

These are the session's most valuable findings — both are *design* bugs that unit tests could not see and would have surfaced on-device weeks from now as "sync feels broken":

**1. Seek-blind filter.** The Kalman filter was never told about executed corrections. After a seek, its error state still carried the pre-seek offset; with post-convergence covariance tight, subsequent fixes barely moved it, so the policy re-seeked forever on a phantom error (sim: 156 seeks, error diverging to 338 ms). Fix: `sc_notify_seek_issued` now shifts the error state by the commanded jump — evaluated at expected *landing* time, not issue time — and inflates variance by a seek-execution term.

**2. Constant landing bias is uncorrectable by seeking harder.** With true command latency 300 ms against a 250 ms prior, every seek landed exactly 50 ms late — and no amount of re-seeking can remove a bias that is re-injected by each seek. The trace showed the loop locked at −50 ms indefinitely. Fix: the policy now *learns* command latency online — the first post-settle estimate after each seek reveals the landing bias, EMA-corrected with clamps. In the final sim it learns 297 ms against a true 300 ms within ~3 seeks.

**Final closed-loop result** (600 s sim: 350 ms initial offset, 500 ppm source skew, 300 ms true vs 250 ms assumed latency, ±3 ms fix noise):

```
34 fixes · 14 seeks · learned latency 297 ms · worst |error| after 60 s = 23.4 ms
```

That satisfies the CORE-03 acceptance criterion (sawtooth inside ±25 ms under 0.05 % skew) with the deadband doing exactly its job.

## Decisions made during implementation (flagging for review)

1. **Session time = input timestamps.** SyncCore never reads a clock; the 15 Hz estimate cadence and recognition scheduler advance on capture-block timestamps. Consequence: estimates/request events only flow while capture flows — which is correct for this product, but worth knowing.
2. **Command-latency learning lives in the policy** (not the estimator) and re-seeds `on_local_seek`. RES-02's measured priors remain worth having for the *first* seek.
3. **Calibration t0 contract:** the shell must call `sc_begin_calibration` at the instant it commands chirp playback, with capture already flowing; t0 is the session's current capture time.
4. **Observation-only drift ID** needs sub-ms fix noise to identify inside 5 ppm — physically inherent (50 ppm ≈ 0.25 ms per 5 s interval). The production drift path is ShazamKit's `frequencySkew`; the test guards the fallback at a looser bound and says so.
5. **CRLF/BOM hygiene:** `.gitattributes` normalizes to LF; commit `a1b79fe`'s subject carries a stray BOM (cosmetic only, left as-is).

Both Visual Studio installs are compiler-front-end-only — **no CRT/STL libs, no `vcvarsall.bat`** — so MSVC cannot link C++ locally. Builds run on a fully portable toolchain (CMake 3.31.6 + llvm-mingw clang 22.1.8) currently living in the session scratchpad, which is **temporary**. Details and remedies in `docs/dev-environment-windows.md`; CI still covers MSVC on `windows-2022`.
